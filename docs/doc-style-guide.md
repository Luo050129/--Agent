# 文档写作与格式规范

> 适用：本项目所有对外文档（README、`docs/*.md`、模块说明）。
> 目的：让第一次打开仓库的人 5 分钟内知道「这是什么、怎么跑、能做什么、做不到什么」，
> 让维护者知道「新内容该往哪加、旧内容什么时候必须同步」。
> 本规范由现有文档反推而来，不是凭空规定——每条规则后面都能在 `README.md`、
> `docs/agent-spec-compliance.md` 里找到例子。

## 一、先分清楚写哪种文档

| 类型 | 位置 | 读者 | 长度 | 回答什么 |
| --- | --- | --- | --- | --- |
| 项目 README（精简门面） | 仓库根 `README.md` | 陌生人、招聘方 | ≤ 150 行 | 这是什么 / 怎么跑起来 / 能干什么 / 结构在哪 |
| 项目 README（完整十节） | 同上 | 想立刻上手的人 | ≤ 350 行，**必须带目录** | 上面这些 + 安装 / 配置 / 示例 / 技术栈 / FAQ |
| 子模块 README | 独立子包或子应用 | 已经决定要用的人 | ≤ 160 行 | 与主项目什么关系 / 关键取舍 / 怎么验证 |
| 深度文档 | `docs/*.md` | 维护者、想复刻的人 | 200~400 行 | 为什么这么设计 / 差距在哪 / 怎么改造 |
| 变更记录 | `CHANGELOG.md`、`prompts/CHANGELOG.md` | 维护者 | 表格，一行一条 | 改了什么 / 为什么 / 影响哪类任务 |
| 代码注释 | 源码内 | 下一个改这段代码的人 | 一段话 | 为什么这么做（不写「做了什么」——代码自己会说） |

**一条铁律**：README 只放「结论 + 导航」，深度内容一律下沉到 `docs/`，用一句话链接过去。
两种风格二选一：精简版超 150 行就说明该拆；完整版超 350 行说明在往 README 里塞文档，该下沉。
完整版必须有目录（带锚点），否则读者滚不到要找的那节。

## 二、文档开头的固定三段

任何文档（README 和 `docs/*` 都一样）开头依次是：

1. **一句话定位**——不要标题，直接一段话说清楚「这是什么」。
   例：`墟是一个**零第三方依赖**的桌面 Agent：读文件、跑命令、接 MCP、从 GitHub 装插件和技能，改坏了能一键撤销。`
2. **机制一句话**——它凭什么做到上面那件事（一句话，不铺陈）。
   例：`内核是一个带自检的 ReAct 闭环——不是「问一次模型、打印一段文本」，而是「思考 → 动手 → 看结果 → 决定下一步」。`
3. **给谁用 / 怎么用**（可选）——一句话降低心理门槛。
   例：`给它方向，不用给它脚本。它卡住会告诉你卡在哪、试过什么、下一步怎么办。`

`docs/*` 类文档改用引用块（`>`）写元信息：适用对象、目的、依据。

## 三之二、完整十节结构（README 的另一种风格）

当项目有安装、配置、示例、FAQ 这些内容需要当场说清（而不是链接出去）时，用十节结构：

```markdown
# 项目名

一句话定位 + 解决什么问题（2~3 句，不要小标题）。

## 📑 目录
- [功能特性](#-功能特性)
- [快速开始](#-快速开始)
- [安装说明](#-安装说明)
- [配置说明](#-配置说明)
- [使用示例](#-使用示例)
- [项目结构](#-项目结构)
- [技术栈](#-技术栈)
- [贡献指南](#-贡献指南)
- [许可证](#-许可证)
- [常见问题](#-常见问题)

---
（以下每节之间用 --- 分隔）

## ✨ 功能特性
## 🚀 快速开始
## 📦 安装说明       ← 要求表（组件 / 要求 / 说明）
## 🔧 配置说明       ← 最小配置 + 配置项表 + 换法示例
## 💡 使用示例       ← 按场景分小节：一次性 / 交互 / 特殊模式
## 📁 项目结构       ← 路径表
## 🧱 技术栈         ← 分层对照表
## 🤝 贡献指南       ← 跑测试的命令 + 代码约定 + 提交前清单
## 📄 许可证
## ❓ 常见问题       ← 用 `**Q：**` 开头，一问一答，问题要是真被问过的
```

**锚点规则（容易踩坑）**：标题带 emoji 时，GitHub 会把 emoji 整段删掉、剩下的空格转成 `-`，
于是 `## ✨ 功能特性` 的锚点是 `#-功能特性`（注意前导 `-`）。两条纪律：

- 目录锚点必须与标题**逐字对应**，加一节就同步加链接
- 只用**单码位 emoji**（`✨ 🚀 📦 🔧 💡 📁 🧱 🤝 📄 ❓`），别用带变体选择符的（如 `⚙️` = `⚙`+U+FE0F），否则锚点会多出空字符

## 四、深度文档骨架（评审 / 分析 / 复刻指南）

```markdown
# 标题（说清文档类型，不只写项目名）

> 评审对象 / 适用范围
> 依据
> 方法（怎么得出这些结论：读代码 + 跑测试 + 抽样记录）

## 结论先行

（一段话给判断，接一张总览表：项目 | 状态 | 一句话结论）

| # | 项 | 状态 | 结论 | 优先级 |
|---|---|---|---|---|

## 逐项拆解

### 1. 项名

#### 要求
（引原文或定义，不解释）

#### 现状与证据
| 要求 | 现状 | 证据（`文件:行`） |
|---|---|---|

#### 差距
（具体到「什么情况下会出什么问题」，不要写「有待完善」）

#### 改造方案
（给代码 / 命令，能直接抄）

#### 验收
（怎么证明改好了：一条命令或一个断言）

## 路线 / 优先级

| 批次 | 内容 | 状态 |
|---|---|---|

## 附：已经做对的（别改坏）

| 能力 | 位置 |
|---|---|
```

**关键**：「现状与证据」必须给到 `文件:行` 或实测输出。没有证据的判断一律不写进文档。

## 五、格式规则（12 条）

| # | 规则 | 正例 | 反例 |
| --- | --- | --- | --- |
| 1 | 表格只用于**对照**（≥2 项可比的属性）；并列要点用列表 | `| 路径 | 作用 |` | 用表格写一个自然段 |
| 2 | 路径、命令、标识符、字段名一律反引号 | `run_shell`、`core/guard.ts` | run_shell 工具 |
| 3 | 代码块必须标语言 | ```` ```bash ````、```` ```ts ```` | ```（空标注） |
| 4 | 表格分隔行统一 `| --- |`，不加对齐冒号 | `| --- | --- |` | `|:---|---:|` |
| 5 | 标题只用 `#` / `##` / `###`，不跳级 | `##` 下接 `###` | `##` 下接 `####` |
| 6 | 中文用全角标点，破折号用 `——`；代码块内一律 ASCII | `是 A——不是 B` | `是A--不是B` |
| 7 | 数字必须具体，且**有唯一来源** | `119 项测试`、`6313 → 1480 token` | 大量测试、明显压缩 |
| 8 | 仓库内链接用相对路径，外链用完整 URL | `[tests](tests)` | `[tests](https://github.com/.../tests)` |
| 9 | 徽章最多 4 个，放最顶（CI / 语言 / 依赖 / 协议） | 4 个 | 8 个堆成墙 |
| 10 | 每条特性一行，格式 `**关键词**：行为 + 细节` | 见 README「特性」 | 一整段形容词 |
| 11 | 强调只用加粗，不用斜体（中文斜体难读） | `**零依赖**` | `*零依赖*` |
| 12 | 占位符统一 `<>`，示例值用真实形态 | `<repo>`、`sk-xxx` | `your_repo_here` |

## 六、内容规则（6 条）

1. **结论先行**：每节第一句就是判断，后面才是论证。读者可以只读每节首句就抓住全文。
2. **给证据不给形容词**：能写「24 个套件 1000 项断言」就别写「测试覆盖充分」；能写 `core/guard.ts:117` 就别写「护栏模块里」。
3. **写清边界**（本项目最看重的一条）：每个能力都要跟一句「做不到什么」。
   例：`图片只能拿到尺寸，别猜画面内容`、`PDF 只解 FlateDecode 流，扫描件解不出来`、
   `沙箱是 patch 层拦截，不是内核级隔离`。**不写边界的能力描述等于骗人。**
4. **不吹**：禁止「业界领先」「革命性」「极致性能」这类词。用数字和机制代替。
5. **可执行**：文档里出现的命令，必须能直接复制粘贴跑通（含前置条件说明）。
6. **数字单一来源**：测试数、token 数、供应商数这类数字，只能在一个地方定义（README 或 manifest / 测试输出），
   其他地方引用它。改了代码必须同步——**陈旧数字比没数字更糟**。

## 七、措辞统一表

同一个概念全项目只用一种叫法，避免同义词漂移：

| 概念 | 统一叫法 | 不要写成 |
| --- | --- | --- |
| 防止任务跑飞的上限机制 | 熔断 | 限流（限流专指每分钟调用上限）、保护 |
| 交付前的自我核实 | 验证式自检 | 自检（自检专指 `--selftest`）、复查 |
| 子进程权限约束 | 沙箱 | 隔离、监狱 |
| 工具结果的失败标记 | `[ERR]` 前缀 / 三层判定 | 错误码（错误码专指 `code` 字段） |
| 会话落盘恢复 | 存档 / `--resume` | 快照、备份 |
| 写文件前的备份 | 检查点 / 撤销 | 回滚、版本 |
| Agent 的两种循环 | ReAct 模式 / Plan 模式 | 普通模式、计划模式 |

## 八、提交前自检清单

写或改完文档，逐条打勾（有任一条不过就别提交）：

- [ ] 开头三段齐了：一句话定位 + 机制一句话 + 价值一句话
- [ ] 每节首句是结论，不是铺垫
- [ ] 所有数字与实际代码/测试输出一致（跑一遍再抄）
- [ ] 每个能力都有一句边界说明
- [ ] 命令能直接复制跑通（前置条件写清）
- [ ] 路径、命令、标识符都加了反引号
- [ ] 代码块都有语言标注
- [ ] 表格只用在对照场景，没有「一段话塞进表格」
- [ ] 仓库内链接用相对路径，且文件真实存在
- [ ] 没有「业界领先 / 极致 / 大幅」这类无信息量的词
- [ ] 新概念已加入「措辞统一表」，没有引入同义词
- [ ] README 行数在所选风格的范围内（精简 ≤150 / 十节 ≤350），深度内容已下沉到 `docs/`
- [ ] 有目录时，每个锚点都能跳到对应标题（emoji 标题的锚点带前导 `-`）
